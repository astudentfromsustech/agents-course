## Answer

For this corpus, do not make a vector store the primary interface. Build a versioned, layout-aware corpus workspace: canonical PDF/repo metadata in `INDEX.md`, stable document/commit/page/section identifiers, searchable extracted text, rendered page/figure/table assets, and agent tools for `find`, `rg`, metadata filtering, targeted reads, and opening the original page. Direct Corpus Interaction (DCI)—agents using grep/file tools—has now been evaluated against sparse, dense, and reranking retrieval baselines and wins on several agentic/multi-hop settings, but the evidence is presently one very recent research line rather than settled production science. [DCI paper](https://arxiv.org/abs/2605.05242)

Add retrieval as a complementary *candidate-generation* tool: BM25/full-text for exact biology identifiers, gene names, flags, APIs, and error strings; dense retrieval for paraphrase/concept discovery; fuse them, rerank, then let the agent inspect the source. A vector index is useful, but it is not the knowledge base and should not be a mandatory gate through which all evidence passes.

Use long context selectively: whole-paper or whole-repository reads after navigation, and possibly whole-corpus prompting only for a small, stable subset. Controlled comparisons generally find long context more accurate when adequately resourced, but much more expensive; a later re-evaluation finds the winner depends materially on document/task structure. [Li et al.](https://aclanthology.org/anthology-files/anthology-files/pdf/emnlp/2024.emnlp-industry.66.pdf) [Li et al., 2025](https://arxiv.org/abs/2501.01880)

Treat PDF extraction as a measured upstream model, not plumbing. Preserve page coordinates, captions, tables and raw PDFs; evaluate it on your own papers before trusting any retrieval result. Citation must resolve to a precise source span/page and retrieval must be evaluated separately from answering.

## Key findings

- The strongest direct “grep/files versus retriever” evidence is Li et al.’s 2026 DCI paper: an agent uses `grep`, `find`, reads, and lightweight scripts over raw corpora—no embeddings/index—and reports gains over sparse, dense, and reranking baselines across BRIGHT/BEIR plus BrowseComp-Plus and multi-hop QA. Its headline average gains are +11.0% agentic search, +30.7% multi-hop QA, and +21.5% IR ranking. This is compelling but still a single, recent research programme; it is not evidence that lexical exploration dominates every corpus or latency budget. [paper](https://arxiv.org/abs/2605.05242) [released code/evaluation logs](https://github.com/DCI-Agent/DCI-Agent-Lite)

- The pro-vector argument remains real: a retriever gives cheap, bounded candidate selection; DCI can scan/explore repeatedly and therefore shifts work to agent tool calls. The follow-on RARG work explicitly identifies DCI’s relevance-agnostic exploration and tool-call cost as a limitation, and proposes relevance as a prior rather than rejecting retrieval outright. [RARG code/paper link](https://github.com/LeqsNaN/RARG)

- “RAG exists only because context windows were small” is too strong. One comprehensive study found long-context models outperform RAG when resources suffice, while RAG has substantially lower cost. [study](https://aclanthology.org/anthology-files/anthology-files/pdf/emnlp/2024.emnlp-industry.66.pdf) A re-evaluation found long context generally better on Wikipedia-style QA, summarization-based retrieval comparable, chunk retrieval worse, but RAG advantageous for dialogue/general queries. [re-evaluation](https://arxiv.org/abs/2501.01880)

- Concrete current economics: Gemini 2.5 Pro exposes a 1M-token context window and lists $1.25/M input tokens for prompts ≤200k tokens; vendor pricing rises above that threshold. Thus repeatedly stuffing a 1M-token corpus is intrinsically priced at corpus scale, whereas retrieval sends a small selected context plus retrieval cost. [Google pricing](https://ai.google.dev/gemini-api/docs/pricing?authuser=2) Anthropic’s practical threshold was that <200k tokens can simply be prompted, especially with caching; this is vendor guidance, not a general benchmark result. [Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)

- Chunking is an information-loss decision: fixed token windows split Methods logic and captions from their figures/tables; sentence/semantic boundaries can isolate anaphora; section chunks improve coherence but dilute retrieval; parent–child retrieval retrieves small children but reads their parent section. These are design consequences to test on the corpus, not universal rankings. Advanced-comparison evidence reports contextual retrieval preserving coherence better but at greater compute, while late chunking is more efficient but can lose relevance/completeness. [comparison](https://arxiv.org/abs/2504.19754)

- Late chunking embeds a long document before pooling token embeddings into chunks, rather than embedding each pre-split chunk; Jina’s implementation uses up to 8,192-token input with its cited encoder. [implementation](https://github.com/jina-ai/late-chunking) The independent comparison above supports a trade-off, not a blanket replication of superior end-to-end QA. [comparison](https://arxiv.org/abs/2504.19754)

- Contextual Retrieval prepends/generated contextual metadata to each chunk for both BM25 and embedding search. Anthropic reports 49% fewer failed retrievals, and 67% with reranking, on its tests; regard these as vendor-reported results until reproduced on the paper/repo corpus. [Anthropic methodology and result](https://www.anthropic.com/engineering/contextual-retrieval)

- A defensible default retrieval stack is: metadata/field filter → BM25 + dense candidates → reciprocal-rank fusion or tuned fusion → cross-encoder/listwise rerank → return source-preserving parent sections/pages. BM25 protects exact strings; dense protects paraphrase; reranking spends an expensive query–passage interaction only on candidates. HYRR reports BEIR and MS MARCO experiments for hybrid-infused reranking, including MS MARCO MRR@10 of 0.4235 versus 0.4222 for its strongest listed T5 reranker baseline; gains are model/dataset dependent. [HYRR](https://aclanthology.org/2024.lrec-main.748.pdf)

- Current practical model choices include BGE-M3 for one model supporting dense, learned-sparse and ColBERT-style multi-vector retrieval over inputs up to 8,192 tokens; ColBERTv2 for late interaction; BAAI bge-reranker variants for local reranking; and Cohere `rerank-v4.0-pro/fast` or `rerank-v3.5` for hosted reranking. [BGE-M3](https://arxiv.org/abs/2402.03216) [ColBERTv2](https://arxiv.org/abs/2112.01488) [Cohere models](https://docs.cohere.com/v2/docs/rerank)

- For scientific PDFs, use a structured extractor, not plain `pdftotext`: GROBID produces TEI with sections, references, figure/table/caption labels and page coordinates, and reports >0.90 reference-instance F1 and >0.95 reference-field F1 in its own evaluation; it is a strong primary text/metadata path. [GROBID](https://github.com/grobidOrg/grobid)

- No universal PDF “error rate” is defensible. A 2023 multi-domain academic-PDF benchmark found GROBID best for metadata/references but Adobe Extract best for tables, with table performance much lower than other element types. [benchmark](https://arxiv.org/abs/2303.09957) For one biomedical figure-extraction test, PDFigCapX achieved 90.67% figure F1—equivalently 9.33% error under that F1 metric—not a whole-document error rate. [study](https://academic.oup.com/bioinformatics/article/35/21/4381/5428177)

- For figures/tables, retain separate assets and link them to caption/page rather than flattening them into prose. PDFFigures2 extracts captioned figures/tables, captions, section titles and bounding boxes but is focused on scholarly computer-science PDFs. [PDFFigures2](https://github.com/allenai/pdffigures2) Nougat is specifically an academic parser for LaTeX math and tables. [Nougat](https://github.com/facebookresearch/nougat)

- Modern parser benchmarks confirm why validation is required: OmniDocBench spans 981 pages, nine PDF types, layout/table/formula annotations, and reports accuracy drops on multi-column/complex layouts; it finds specialized pipelines stronger on common academic pages and tables, while VLMs can generalize better to visually degraded/unusual pages. [OmniDocBench](https://arxiv.org/abs/2412.07626)

- GraphRAG is not a default replacement for hybrid retrieval. Microsoft’s original GraphRAG targets “global” corpus questions by extracting entities/relations, communities and summaries; its claims are mainly about open-ended global sensemaking, not point QA. [original paper](https://arxiv.org/abs/2404.16130) A systematic RAG-versus-GraphRAG study reports task-dependent outcomes and shortcomings, rather than a universal GraphRAG win. [systematic evaluation](https://arxiv.org/abs/2502.11371) Build a graph only where the corpus already supplies high-value typed relations—paper↔dataset↔method↔software↔version, citations, APIs, workflow inputs/outputs—and benchmark multi-hop questions against the simpler stack.

- In current practice, *memory* is durable, selectively maintained state about the user/agent’s past interactions, preferences, decisions and task progress; *corpus retrieval* accesses externally authoritative documents/code. They may use the same storage/search mechanisms but need different write policy, temporal semantics, deletion, and trust model. LongMemEval evaluates extraction, multi-session and temporal reasoning, updates and abstention. [LongMemEval](https://arxiv.org/abs/2410.10813)

- Persistent-memory designs are unsettled: a 2026 comparison found long-context GPT-5-mini higher on factual recall in LongMemEval/LoCoMo, while fact extraction competed where stable persona attributes mattered. [cost–performance study](https://arxiv.org/abs/2603.04814) Do not let a memory summarizer overwrite or silently supersede the paper/repository corpus.

- Evaluate in layers. Build gold questions with exact evidence spans, then measure document/section/page **recall@k**, MRR/nDCG and candidate-set coverage before generation; separately measure answer correctness, claim-level entailment/faithfulness, abstention, and citation precision/recall. RAGChecker explicitly separates retrieval and generation diagnostics and reports better correlation with human judgement than comparator metrics in its meta-evaluation. [RAGChecker](https://arxiv.org/abs/2408.08067) RAGAS is a reference-free alternative, but should be calibrated against expert review for a scientific corpus. [RAGAS](https://arxiv.org/abs/2309.15217)

- Wrong-chunk grounding is detectable only if every answer claim carries immutable chunk/page/span IDs and an independent entailment check runs against the *cited original span*, not a lossy summary. This matters: a 2026 attribution study measured 0.86 citation precision against summaries but 0.12 against recovered source spans for one compressed ASQA setting. [study](https://arxiv.org/abs/2609.14245)

- Suitable public evaluation materials include BEIR for zero-shot IR, BRIGHT for reasoning-intensive retrieval, QASPER for scientific-paper QA, ScholarQABench for literature synthesis/citations, and TREC RAG for end-to-end RAG. [BEIR](https://arxiv.org/abs/2104.08663) [BRIGHT](https://arxiv.org/abs/2407.12883) [QASPER](https://arxiv.org/abs/2105.03011) [ScholarQABench](https://www.nature.com/articles/s41586-025-10072-4) [TREC RAG](https://trec-rag.github.io/)

- Provenance/staleness practice should be content-addressed and append-safe: retain original PDF/repo commit, extraction-tool/model version, extraction timestamp, page/coordinates/section path, chunk hash and supersession/deletion events; cite the immutable source span, not merely a document title. Directly evaluate citation precision (does it entail the claim?) and citation recall/completeness (are all citation-worthy claims supported), as ScholarQABench does. [ScholarQABench citation protocol](https://www.nature.com/articles/s41586-025-10072-4)

## Caveats and open questions

- The DCI result is the closest genuine head-to-head evidence, but it is recent, centred on IR/agentic benchmarks rather than a 200-paper-plus-50-repository computational-biology corpus, and its reported gains need independent replication. [DCI](https://arxiv.org/abs/2605.05242)

- There is no published result I could verify that directly compares DCI, hybrid retrieval, GraphRAG, and 1M-context prompting on the exact mixed scientific-PDF/code-repository setting. The recommended architecture is therefore an evidence-informed starting point, not a claimed optimum.

- Long-context price, latency and accuracy are model/provider/cache/workload dependent. The literature supports the cost/accuracy trade-off but does not supply one durable “1M versus RAG” latency number. Measure prefill latency, tool-call latency, input tokens, total cost, and task accuracy under your chosen API/model. [LC/RAG study](https://aclanthology.org/anthology-files/anthology-files/pdf/emnlp/2024.emnlp-industry.66.pdf)

- Parser scores are not interchangeable: extraction accuracy varies by publisher PDF encoding, scanned versus born-digital documents, equations, multi-column order, supplements and the definition of correctness. A universal scientific-PDF error rate is therefore **[unverified]**; sample and manually adjudicate your own corpus. [OmniDocBench](https://arxiv.org/abs/2412.07626)

- Evidence that reranking/hybrid search “always” improves an agent is thin outside benchmark-specific configurations; its value should be established with an ablation matrix over your gold questions, not adopted on reputation alone. [HYRR](https://aclanthology.org/2024.lrec-main.748.pdf)

- Graph extraction quality, entity resolution, relation schema and maintenance cost often dominate GraphRAG outcomes, and the available systematic literature does not justify its marketing as a universal RAG upgrade. [systematic evaluation](https://arxiv.org/abs/2502.11371)
